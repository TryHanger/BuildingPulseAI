## 0. Изменение разрешений относительно прежних заданий

Пользователь **явно разрешил Git commit и Git push в указанный GitHub-репозиторий**, чтобы заменить передачу ZIP-пакетов. Предыдущий запрет `no commit/no push` в прежнем задании Stage14 отменяется **только применительно к этому репозиторию и описанной ниже процедуре**. Остальные ограничения сохраняются: **никаких deploy, изменений production, принудительной перезаписи истории, автоматических merge или изменений действующих эксплуатационных FDD-правил**. Внешние GitLab/Sensata репозитории не затрагивать.

Ты — **единственный агент S** для backend, frontend, науки, тестов и публикации. Работай с текущим локальным BuildingPulse, не создавай новый пустой проект вместо существующего.

## 1. Однократная инициализация репозитория

1. Сверь текущую локальную рабочую копию со стадией `BP-ML-FIELD-REPLICATION-13`, ранее принятой как `ACCEPT_EXPLORATORY_DESCRIPTIVE`. Проверь, что эта копия действительно включает действующий backend, frontend, исследовательские модули и обязательные тесты, а не только минимальную папку Stage13.
2. Так как удалённый репозиторий пока пуст, после предварительной санитарной проверки создай **исходный baseline-коммит Stage13 в `main`** и отправь его в `origin/main` обычным push. Перед пушем повторно проверь пустоту удалённого репозитория; если он уже изменился, остановись и не перезаписывай его.
3. Сохрани фактический baseline SHA (`STAGE13_BASE_SHA`). Этот SHA является точкой сравнения для следующего аудита.
4. После baseline создай ветку **`research/field-apar-gate-14`** от принятого `main`. Все изменения Stage14, исследовательские протоколы, числовые результаты и тесты публикуй **только в этой ветке**.
5. Открой **draft Pull Request** из `research/field-apar-gate-14` в `main`. Не нажимай Merge. В следующем этапе используй новую ветку от последней принятой версии, а не меняй прошедший аудит commit.

Если в локальной копии уже есть Git-история или другие remotes, сначала проверь `git remote -v`, ветки и текущие незакоммиченные изменения. Не делай `git init` поверх существующей истории и не используй `git push --force`. Сохраняй исходные изменения и происхождение файлов.

## 2. Что обязательно хранить в GitHub

В коммитах должны быть все **необходимые для аудита, распространения и воспроизведения** материалы:

- Полный исходный код существующего BuildingPulse (backend, frontend, research/ML, миграции, Docker/Compose конфигурация, обработка данных, API, UI) и тесты.
- Воспроизводимые версии зависимостей и lock-файлы; инструкции запуска/тестирования для Windows и Linux, когда применимо.
- Задания, предрегистрации, research decision ledger, источник правил, таблицы контрактов датчиков и ограничения научных выводов.
- Для каждой стадии: скрипты расчётов, **небольшие** результаты CSV/JSON, негативные и STOP-результаты, полные краткие тестовые логи, SHA-256 источников/артефактов, сравнительные диффы или manifest, инструкции воспроизведения.
- Документацию с точной версией входных исходных данных, DOI/URL, способом повторного скачивания, процедурами верификации SHA-256 и числом независимых наблюдений; provenance модельных весов, если они включены.
- Для Stage14 желательная структура: `research/field_apar_gate_14/` (код и тесты) и `research/evidence/field_apar_gate_14/` (научные протоколы, контрольные суммы, результатов сравнения, отчёт и компактные журналы). Можно сохранить устоявшиеся рабочие пути проекта; **не ломать импорты и маршруты ради структуры**.

**Не помещать в обычные коммиты:** `.env` и пароли, токены, ключи/API, внутренние URL с секретами, персональные данные, продовые БД/дампы, чужие закрытые материалы, `node_modules`, `.venv`, кеши, сотни мегабайт исходных LBNL/G36/Mendeley файлов, большие XLSX/ZIP, бинарные временные файлы. Поддерживай `.gitignore`/`.gitattributes`; выполни ручной поиск секретов в `git diff --cached`, файлах и истории **перед первым публичным push**. Если в уже имеющемся коде обнаружен секрет, не публикуй его; сообщи владельцу и остановись до безопасного решения.

Для больших неизменных исходных источников — точный URL/DOI, SHA-256, описание получения и проверочный скрипт. Для **собственных** крупных результатов, если они действительно необходимы, используй только заранее подходящий Git LFS/GitHub Actions artifact/Release с проверкой размера, лицензии и доступа; ссылку и SHA в репозитории. Ничего не опускай молча.

## 3. Выполни ранее согласованный Stage14 без изменения научной постановки

Продолжай оригинальное задание `TASK_SINGLE_AGENT_S_BP_ML_FIELD_APAR_GATE_14.md` из последнего пакета аудита Stage13. **Суть не менять**:

1. Перечитать первоисточник Nehasil et al. 2021 и исходные Mendeley workbooks; проверить SHA-256 всех восьми оригинальных исходных файлов.
2. Найти **одно** физическое APAR-подобное правило, зафиксировать точное происхождение, входы, роль каждого BAS-тега, применимость, режим и порог. Если параметры статьи не раскрыты — явно `APAR_INSPIRED_NOT_PAPER_REPLICATION`, никакого ложного заявления о воспроизведении `94/105`.
3. До оценки зафиксировать предрегистрацию, пороги и машинно-читаемые манифесты.
4. Сформировать **полный** ledger пригодных сравнительных 5-минутных окон, не выбирая благоприятные по исходу, без интерполяции и смешения publisher fault labels с входными признаками.
5. Только если Gate A и Gate B пройдены, провести **ограниченное исследовательское сравнение** APAR-подобного правила с наивным SAT-drop и показать все отрицательные результаты; иначе честный STOP.
6. Никаких новых ML-моделей, перенастройки LightGBM или включения эксплуатационного FDD.

## 4. Приёмка и GitHub-отчёт вместо ZIP

По завершении **НЕ собирай очередной `*_REVIEW.zip`**. Весь результат публикуй в branch и draft PR; в PR description/`research/evidence/.../REVIEW_INDEX.md` дай:

- `repo`, `base branch`, `base SHA`, `review branch`, `head SHA`, **ссылку на draft PR**;
- перечень реально изменённых файлов, краткую сводку и перечень неизменённых критических контрактов;
- статус Gate A / Gate B / научный вердикт; список `CLAIM / NOT CLAIM / STOP`;
- точные версии Python/Node/библиотек, CLI-команды для тестов, результаты тестов (PASS/FAIL/SKIP, причины), и замечания к Docker/Playwright;
- ссылку на исходный publication dataset, список SHA-256 и пути к скриптам независимого воспроизведения;
- полные, но компактные доказательные таблицы, включая негативные случаи, недопустимые окна и недостаток данных;
- описание каких тестов/исходников **не было**, без маскировки отсутствующих проверок;
- подтверждение, что никакие секреты/большие исходные данные не включены и `main` не менялся после bootstrap.

**Не продолжай автоматически Stage15 и не мержи PR.** Пользователь отправит ссылку на ветку или PR, а независимый ChatGPT прочтёт код через GitHub connector, проверит diff/версии/артефакты и определит следующий этап.

## 5. Короткий формат ответа владельцу

```text
Repo: https://github.com/TryHanger/BuildingPulseAI
Baseline: main @ <SHA>
Review branch: research/field-apar-gate-14 @ <SHA>
Draft PR: <URL>
Gate: <GO/STOP и причина>
Tests: <n passed, n failed, n skipped; какие именно>
Evidence index: <URL на REVIEW_INDEX.md>
Uncommitted changes: <пусто или список и причина>
```

Ограничение публикации: `main` после bootstrap не трогать, никаких auto-merge/force-push/deploy. Все научные утверждения должны быть подкреплены файлами конкретного commit SHA.
