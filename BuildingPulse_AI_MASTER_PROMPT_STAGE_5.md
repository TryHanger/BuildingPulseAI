## 2. Приоритетные методологические дефекты Stage 4 — исправить ПЕРЕД Stage 5

### 2.1. «Physical refutation» при совпадении команды и положения клапана (P0)

В `docs/DECISIONS.md` заявлено: если `abs(CHWC_VLV_DM-CHWC_VLV)<0.05`, гипотезу `VALVE_STUCK` физически исключают. **Это логически неверно в общем случае.** Заклинивший на 25% клапан и команда 25% совпадут, но неисправность никуда не исчезнет. Совпадение в отдельной точке, при постоянной команде или в период запаздывания не доказывает исправность.

Требования:
- Найди все места, где это условие обнуляет класс, повышает класс `SENSOR_BIAS` или выдаёт `CONFIRMED_BY_FEEDBACK`.
- Заменяй категорическое опровержение на **условное временное свидетельство tracking**, которое требует достаточного изменения команды, достаточного горизонта, допуска на реакцию и стабильной обратной связи. Пример начальной формализации (только кандидат для калибровки): на прошлом окне 30–60 минут команда изменилась на >=0.15 доли, положение в допустимой задержке отреагировало на сравнимую величину, и ошибка слежения удерживалась <0.05 там, где динамика установилась. Все гиперпараметры выбрать на train/validation, не на тесте. При отсутствии возбуждения (`no excitation`) — `INSUFFICIENT_ACTUATOR_EXCITATION`, а не «клапан исправен».
- Тесты: (A) заклинивший на 25% и команда 25% => нельзя исключить `VALVE_STUCK`; (B) команда меняется 20→70%, фактическое положение остаётся 25% => свидетельство неисправности; (C) команда меняется и положение отслеживает после допустимой задержки => умеренное контрсвидетельство stuck, но не доказательство отсутствия leakage; (D) недоступный/зашумлённый/несинхронный feedback => недостаточно свидетельств; (E) постоянно закрытая команда 0% и feedback 0% => нет оснований для refutation; (F) stuck на уровне, совпадающем с частью траектории команды.
- Не объединяй `VALVE_STUCK` и `VALVE_LEAKAGE`: leakage возможна даже при корректном положении исполнительного механизма. Ни одно правило совпадения команды/позиции не исключает утечку через седло.
- Добавь безопасные статусы `SUPPORTS`, `CONTRADICTS_CONDITIONALLY`, `INCONCLUSIVE`, `UNAVAILABLE` и основания для каждого.
- До и после исправления сравни Decision Layer, отдельно отчитай, какие оценки изменились. Не маскируй снижение метрик; ошибки правила важнее удобного F1.

## 4. Gate C — реализация Sensor Recommendation Engine

### 4.1. Математическая постановка

Пусть `p` — текущий профиль, `J(p)` — разрешённые дополнительные каналы, `R_p(c)` — селективный риск при Coverage c на validation с согласованными eligibility и target. Для каждого `j`:

`V_j(c) = R_p(c) - R_{p+j}(c)`.

Это **эмпирическая оценка**, не универсальная полезность и не калиброванная вероятность. Она может быть отрицательной. Записывай `coverage_actual`, число оценённых окон/эпизодов, устойчивость по независимым сценариям и причины невозможности сравнения.

Если `V_j>0` только на одной severity и хуже на других, рекомендация не должна подаваться как надёжная: верни явное ограничение и результаты по сценариям. Поддержи `NO_RELIABLE_RECOMMENDATION`.

### 4.2. Алгоритм выбора

- Реализуй `SensorRecommendationService` с чистым интерфейсом `recommend(context, current_profile, candidate_channels, validation_artifacts) -> RecommendationResult`.
- В первом MVP допустима **глобальная или режимно-условная** recommendation policy, обученная на validation. Для выдачи индивидуальной рекомендации по каждому тестовому эпизоду необходимо иметь проверенные условия режимной стратификации и недостаточно использовать скрытые значения отсутствующих каналов.
- Перед ранжированием проверяй `profile`/channel availability, units, физическую принадлежность AHU, legal operating mode, обязательные каналы, версию модели и покрытие валидации.
- Для каждого кандидата тренируй/калибруй совместимую модель **с нуля по соответствующему whitelist** на одинаковых тренировочных группах или используй заранее воспроизводимый family model registry. Нельзя «для Basic» применять Full-модель, даже если в UI скрыть дополнительные поля.
- Валидационная оценка `j` может законно смотреть на этот канал **на validation**, поскольку задача — оценка ценности его потенциального добавления. **На тестовом эпизоде при выборе нельзя смотреть на значение скрытого `j`**, иначе возникает утечка.
- После выбора при офлайн-оценке можно открыть выбранный канал, пересчитать прогноз и записать фактический gain на held-out. Не открывай другие кандидаты для принятия решения.
- Запиши abstention reasons: insufficient_groups, incompatible_channels, out_of_domain, no_positive_evidence, tie_or_unstable_ranking, no_excitation, no_validated_model.

### 4.3. Три честных baseline выбора

1. **Random:** случайный из того же списка допустимых каналов; много повторов с фиксированными seeds, отчёт среднего и разброса, не один удачный случай.
2. **Fixed:** один заранее выбранный канал, например `CHWC_VLV` — до теста и без ретроспективного изменения.
3. **Validation-based:** наш рекомендатель.

Обязательно сравнивай в одной постановке, на одинаковых тестовых сценариях и одинаковом бюджете 1 канал. В дополнение можно показывать post-hoc Oracle как **недостижимую верхнюю оценку с явно запрещённым использованием в реальной рекомендации**; Oracle не является честным конкурирующим алгоритмом и не должен фигурировать как достигнутый результат.

### 4.4. Контракт результата

Пример DTO (поля уточни под существующие Pydantic-модели, не ломай текущие API):

### 4.5. API

Сохраняй существующие эндпоинты. По возможности добавь:

Результаты должны кэшироваться с ключом model hash + dataset version/hash + profile + policy + validated split + scenario/window. Избегай скрытой зависимости от текущего UI. Повторный запрос не должен изменять экспериментальные данные.

**Gate C:** алгоритм реально выполняется на валидированных сценариях, API возвращает информативные результаты без тестовой/меточной утечки, есть тесты позитивного, отрицательного и неопределённого результата.

## 5. Gate D — эксперимент H3 и научная оценка рекомендаций

Создай исполняемый модуль `ml/diagnostics/evaluate_stage5_recommendations.py` и отчёт `research/reports/STAGE5_RECOMMENDATION_REPORT.md`.

Выходные таблицы:

- per-scenario: class, severity, split, allowed candidate list, выбранный канал, validation `V_j`, measured held-out delta after selection, eligible episodes, coverage, risk, set coverage, counts, availability flags;
- per-strategy: Random (mean/stdev over seeds), Fixed, Validation-based; одинаковый test set;
- per-profile: Basic и дополненные варианты;
- per-class: SensorBias / ValveStuck / DamperStuck;
- failure cases: зачем recommendation не сработала (режим, слабый сигнал, неподходящие каналы, мало данных).

Создай графики (минимум):

1. `stage5_channel_value_validation_vs_test.png` — выбор на validation и честный gain на held-out;
2. `stage5_recommender_strategy_comparison.png` — Random/Fixed/Validation-based с указанием sample size;
3. `stage5_recommendation_abstention.png` — сколько случаев без надёжной рекомендации и почему;
4. **если данные позволяют** — раздельный risk–coverage по профилям и стратегиям.

Необходимо в явном виде вычислить **stability**: как часто лучший канал меняется при изменении withheld scenario/severity или временного блока; при малом числе групп не подменяй устойчивость процентов точной вероятностью.

Наличие дополнительного канала может **не** улучшать F1 или risk. Не скрывай отрицательные `V_j` и не переименовывай результат в успех. Если Fixed превосходит recommended, вывод H3 = `NOT_SUPPORTED` при данной постановке.

Если профили содержат «канал напрямую выдаёт зафиксированное в симуляции положение» и почти напрямую кодируют класс stuck, назови это ограничением benchmarks; не выдавай как универсальный эффект в реальном здании.

**Gate D:** итог воспроизводим одной CLI-командой из существующего проекта, имеется валидный JSON манифест и таблица всех независимых исходных групп; нет нерешённых критических тестовых утечек.

## 6. Gate E — независимые реальные данные (CSIRO / RBC-Nesbitt)

### 6.1. Источники и приоритет

Основной кандидат: CSIRO AHU Fault Detection Dataset — рабочая BMS реального офисного здания (Newcastle, Australia), вводимые в управление неисправности клапанов/заслонок/датчиков; GitHub: `https://github.com/csiro-energy-systems/ahu-fault-detection-dataset`; данные через Git LFS; лицензия данных CC BY-SA 4.0. Второй: RBC-Nesbitt, Drexel University (реальные измерения из публикации Scientific Data 2026), доступ через Figshare и документацию. Источники проверить по официальной публикации/репозиторию, не угадывать имена колонок и метки.

### 6.2. Этапы работы с реальным набором

1. Проверить доступ, лицензирование, file size, ZIP/LFS, checksum, версии; если LFS недоступен, попробуй документированный официальный альтернативный путь, не подменяй другим фейковым CSV.
2. Прочитать data dictionary и Ground Truth protocol. В CSIRO осмысленно применить штатный метод сопоставления telemetry ↔ fault intervals, если подтвержден документированным кодом. Во внешнем датасете не все fault labels обязательно соответствуют трём классам LBNL.
3. Создать `docs/EXTERNAL_DATASET_COMPATIBILITY.md`: для каждого нужного канала LBNL — его внешний кандидат, unit conversion, физическая эквивалентность, sampling interval, source mechanism, status `MAPPED` / `UNAVAILABLE` / `AMBIGUOUS`. Никакой фантазии при отсутствии данных.
4. Реализовать отдельный адаптер `scripts/import_csiro.py` ИЛИ `scripts/import_rbc_nesbitt.py`, с тестовыми фикстурами, сохранением raw immutable, Parquet processed и provenance. Не менять каноническую семантику LBNL ради второго источника.
5. Реализовать минимум **визуализацию реальной телеметрии**, временные границы реального fault event, provenance badge `REAL_FIELD_BMS` (либо более точный тип), quality checks и event viewer. Если возможно, отобразить корректные предупреждения инженерных правил с обозначенными границами применимости.
6. **Запрещено** просто подавать реальное здание в LBNL LightGBM и выдавать вывод как `VALIDATED`. Допустимо экспериментальное `OUT_OF_DOMAIN_UNVALIDATED` только явным действием с яркой маркировкой; валидированный вывод возможен лишь после отдельной верификации в целевом домене и достаточной калибровки.
7. По возможности проверить transferable subset (например, quality checks, physical command-feedback mismatch) и метрики на совместимых размеченных эпизодах. Если прямой ML-transfer невозможен, представить **доказанный отрицательный/ограниченный результат**, а не писать «внешняя валидация PASS».
8. Если оба источника недоступны, документировать URL, ошибки, воспроизводимые команды получения и constraints. Не ставить PASS на «validated external building»; можно отдельно поставить PASS на адаптер при локальных фикстурах, а внешнему эксперименту статус BLOCKED.

**Gate E:** хотя бы одно внешнее реальное свидетельство в продукте с корректной маркировкой либо честно зафиксированный блокер, причём критерий «валидирована ML-модель на реальном здании» никогда не считается выполненным без реального эксперимента.

## 7. Gate F — отдельная страница «Исследования» и UX

Создай отдельную реальную страницу, а не огромный блок внизу «Диагностики». Сохрани мониторинг и диагностику без регрессий. Три раздела веб-приложения: **Мониторинг AHU**, **Диагностика**, **Исследования**.

### 7.1. Раздел «Исследования»

Разбей на небольшие внутренние вкладки:

- **Обзор экспериментов:** H1/H2/H3, источник данных, versions, status (confirmed on test / exploratory / blocked), number of independent scenarios, run ID, timestamp.
- **Risk–Coverage:** B1/B2/Decision Layer по одному профилю, отдельный переключатель профиля; контекст N, denominator, conditional vs end-to-end. Обязательно не вводить в заблуждение сравнением разных наборов данных.
- **Наблюдаемость:** Basic/Valve/Damper/Both/Full, F1 по семействам, матрицы ошибок, число каналов, ясно указанные дополнительные измерения.
- **Рекомендации измерений:** selector текущего профиля, top candidates, validation benefit и held-out experiment outcomes с чётким разделением «оценено заранее / проверено после», причины отсутствия рекомендации.
- **Реальные здания:** импортированный CSIRO/RBC с реальными временными рядами, fault labels только в исследовательском режиме, совместимые/недоступные каналы, статус Domain Guard, limitations.

### 7.2. Пользовательский сценарий

1. Открывает Basic и реальный размеченный LBNL-сценарий.
2. Видит обнаруженную аномалию и `MULTIPLE_PLAUSIBLE`/`CAUSE_UNRESOLVED`, если это реально следует из механизма.
3. Нажимает «Какое измерение поможет?».
4. Система показывает validation-ranked кандидатов и основания. При отсутствии оснований — объясняет это.
5. Пользователь явно переключает профиль/включает выбранный канал.
6. Видит пересчёт диагностики на **той же временной истории**, без изменения метки Ground Truth.
7. В «Исследованиях» видит независимые результаты сравнения с Random и Fixed.
8. Переключает внешний набор и видит реальный источник с отдельными ограничениями применимости.

### 7.3. UX и отображение

- Не перегружай верхний мониторинг исследовательскими таблицами.
- Не показывай проценты «вероятности неисправности», если score не калиброван.
- Не выдавай `NO_ANOMALY` как «исправно доказано».
- Пустые состояния и ошибки API должны объяснять почему нет результата: profile incompatible / no valid model / no validation groups / insufficient samples / external data unavailable.
- Loading/progress/dataset size, форматные русские подписи, единицы измерения, responsive layout, клавиатурный доступ.
- Генерируй реальные скриншоты через Playwright, не подменяй их макетами.

**Gate F:** user-visible end-to-end workflow через backend, screenshot доказательство каждой новой функции, отсутствие заглушек «всегда рекомендуем клапан».

## 8. Gate G — тесты и инварианты

**Сохрани существующие 33 теста, добавь достаточное количество новых, но не гонись за числом ради отчёта.** Обязательно покрыть:

### Научные тесты

1. Valve stuck 25% + command 25% => **нельзя физически опровергать stuck**.
2. Сильно меняющаяся команда + положение остаётся неизменным => сильное свидетельство stuck.
3. Постоянная команда + совпадающее положение => `INCONCLUSIVE`, а не `VALVE_HEALTHY`.
4. Динамическое следование с запаздыванием => корректный tracking на проверенном окне.
5. Valve leakage не исключается из-за правильного положения привода.
6. Missing feedback не эквивалентен нулевому feedback.
7. `BASIC` исключает расширенные колонки при обучении, инференсе, features и API; изменение скрытых данных не влияет на вывод.
8. Training/candidate-selection не видит held-out labels и недоступные test channels.
9. Если кандидаты плохи или данных мало, recommender возвращает `NO_RELIABLE_RECOMMENDATION`.
10. Разные seeds Random используются как полный распределённый baseline; Fixed действительно выбран до теста.
11. Валидационный кандидат и post-hoc Oracle нельзя спутать.
12. Risk/coverage и set metrics корректны при нулевом охвате, множественных диагнозах, пропущенных истинных аномалиях, неравной длине сценариев.
13. Сравнение H1 same-profile, H2 same-method, H3 same-test cases.
14. Ни `source_fault_label`, ни `scenario_id`, ни filename не участвуют в реальном inference/features.
15. Domain Guard закрывает выдачу валидированных прогнозов для другой физической системы без явно подтверждённой целевой валидации.

### Технические тесты

- API schema/422/404/409, отсутствующий канал, неизвестный profile, недоступный model, невалидное время, некорректные единицы.
- SQLite/PostgreSQL режимы при доступности, Parquet import, cache key, provenance, идемпотентность.
- `npm --prefix frontend run build`, `pytest backend/tests`, research CLI, Playwright полного сценария.
- `docker compose config` и попытка `docker compose up --build -d`. При DNS fail — документировать stdout/stderr и не заявлять runtime PASS.
- Проверить расчёт ресурсов при больших CSV и масштабирование графиков, отсутствие NaN/Inf в JSON.

Скриншоты в `docs/screenshots/stage5_*.png`: recommender candidates, abstain, переключение профиля с пересчётом, research risk–coverage, strategy comparison, external dataset, domain guard.

**Gate G:** все необходимые тесты действительно запущены; PASS/FAIL/BLOCKED записаны без оптимистичной трактовки.
