# STAGE 4 DECISION LAYER SPECIFICATION — Спецификация формального слоя принятия решений

- **Версия:** 1.0 (Formal Spec)
- **Дата:** 2026-11-02
- **Компонент:** `ml/diagnostics/decision_layer.py`
- **Конфигурация:** `ml/diagnostics/config/decision_layer_v1.yaml` (или embedded defaults)

---

## 1. Назначение и архитектурное место

Decision Layer — это детерминированный, проверяемый программный модуль, который принимает на вход:
1. Результаты детектора аномалий (`anomaly_detected`, `anomaly_score`);
2. Вектор оценок вероятностей или сырых скоров классификатора семейств неисправностей $P(C_k)$;
3. Набор физических свидетельств $E = \{e_j\}$ (невязка виртуального датчика, согласованность команды и положения приводов, температурные градиенты смешения);
4. Флаги качества данных и эксплуатационного режима (вентилятор включен, установившийся режим, полнота измерений);
5. Профиль наблюдаемости (`BASIC`, `BASIC_PLUS_VALVE`, `BASIC_PLUS_DAMPER`, `BASIC_PLUS_BOTH`, `FULL`).

И вырабатывает категориальное диагностическое заключение с объяснением причин:
- `SINGLE_CAUSE`: Единственная правдоподобная и физически подтвержденная причина;
- `MULTIPLE_PLAUSIBLE`: Набор из 2 или более конкурирующих причин при недостатке разделяющих свидетельств;
- `CAUSE_UNRESOLVED`: Аномалия присутствует, но доступных свидетельств недостаточно для идентификации даже группы;
- `NO_ANOMALY`: Аномалий не обнаружено в поддерживаемом рабочем режиме;
- `AHU_OFF`: Оборудование остановлено, диагностика не проводится;
- `INSUFFICIENT_DATA`: Отсутствуют критические каналы для базовой детекции;
- `OUT_OF_DOMAIN`: Источник данных не валидирован на совместимость (Domain Guard).

## 2. Формальные правила перехода и вентили (Diagnostic Gates)

```mermaid
flowchart TD
    Start([Вход: окно телеметрии + профиль]) --> G_Dom{Domain Guard?}
    G_Dom -- Нет --> R_Domain[OUT_OF_DOMAIN_UNVALIDATED]
    G_Dom -- Да --> G_Op{SF_SPD >= 0.5?}
    G_Op -- Нет --> R_Off[AHU_OFF]
    G_Op -- Да --> G_Qual{Качество данных OK?}
    G_Qual -- Нет --> R_Qual[INSUFFICIENT_DATA]
    G_Qual -- Да --> G_Anom{Аномалия обнаружена?}
    G_Anom -- Нет --> R_Normal[NO_ANOMALY]
    G_Anom -- Да --> EvidenceEval[Вычисление свидетельств и скоров классов]
    EvidenceEval --> G_Admissible[Отбор допустимых гипотез Gamma]
    G_Admissible --> CheckCount{Количество гипотез |Gamma|}
    CheckCount -- = 1 и достаточные свидетельства --> R_Single[SINGLE_CAUSE]
    CheckCount -- >= 2 --> R_Multi[MULTIPLE_PLAUSIBLE]
    CheckCount -- = 0 или конфликт --> R_Unres[CAUSE_UNRESOLVED]
```

### 2.1. Вентиль допустимости гипотезы (Admissibility Gate)
Семейство $C_k \in \{\text{SENSOR\_BIAS\_SA}, \text{COOLING\_VALVE\_STUCK}, \text{OUTDOOR\_DAMPER\_STUCK}\}$ признается допустимой гипотезой $C_k \in \Gamma$, если:
1. **Вероятностный порог жизнеспособности:** $P(C_k) \ge \tau_{\text{viable}}$ (по умолчанию $\tau_{\text{viable}} = 0.20$);
2. **Отсутствие прямого опровержения:** Нет сильного физического свидетельства, категорически исключающего данный класс (например, если доступен датчик `CHWC_VLV` и $|CHWC\_VLV\_DM - CHWC\_VLV| < 0.05$, то заклинивание клапана охлаждения опровергнуто);
3. **Физическая применимость:** Дефект имеет возможность проявиться в текущем режиме работы (например, если наружная температура близка к уставке, заклинивание заслонки может быть неразличимо).

### 2.2. Критерий выдачи единственного диагноза (`SINGLE_CAUSE`)
Заключение `SINGLE_CAUSE` с кандидатом $C^*$ выдается **тогда и только тогда, когда одновременно выполнены все условия**:
1. $|\Gamma| = 1$ (ровно один кандидат прошел отбор допустимости), либо для лидирующего кандидата $C^*$ обеспечен отрыв по вероятности:
   $$P(C^*) - \max_{C_k \neq C^*} P(C_k) \ge \Delta_{\text{margin}} \quad (\text{по умолчанию } \Delta_{\text{margin}} = 0.35)$$
2. Имеются подтверждающие физические свидетельства ($S(C^*) > 0$);
3. Отсутствуют неразрешенные конфликты свидетельств;
4. В профиле `BASIC` при отсутствии датчиков положения штоков:
   - Если симптомы совместимы и со смещением датчика, и с малым заклиниванием клапана (например, в установившемся режиме без явного рассогласования теплового баланса), система **запрещает** выдачу singleton и обязана перевести статус в `MULTIPLE_PLAUSIBLE` (набор $\{C_{\text{sensor}}, C_{\text{valve}}\}$).

## 3. Машинно-читаемые коды причин (Reason Codes)

Каждое заключение сопровождается списком кодов причин:
- `CONFIRMED_BY_FEEDBACK`: Подтверждено прямым датчиком положения штока привода.
- `REFUTED_BY_FEEDBACK`: Опровергнуто прямым датчиком положения штока привода.
- `CONFIRMED_BY_THERMAL_BALANCE`: Подтверждено рассогласованием теплового баланса смешения.
- `AMBIGUOUS_WITHOUT_VALVE_FEEDBACK`: Неоднозначность между смещением датчика и клапаном из-за отсутствия `CHWC_VLV` в текущем профиле.
- `AMBIGUOUS_WITHOUT_DAMPER_FEEDBACK`: Неоднозначность из-за отсутствия `OA_DMPR` в текущем профиле.
- `SIMILAR_MODEL_SCORES`: Близкие значения скоров классификатора для нескольких классов.
- `LOW_CONFIDENCE`: Все модельные скоры ниже минимального порога достоверности.
- `DATA_QUALITY_DEGRADED`: Выявлены пропуски или подозрительные значения в измерительных каналах.
- `OPERATING_MODE_OFF`: Вентилятор остановлен, оборудование выключено.
- `OUT_OF_DOMAIN_BENCHMARK`: Доменный барьер предотвратил невалидированный инференс на синтетических данных.
