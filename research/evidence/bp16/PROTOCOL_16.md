# BP-16 · протокол пилотной оценки решений

Версия `bp16-pilot-v1`. База BP-15 `ab99ff28c99be9fc93e4fab6abc2748e2b7fd904`, статус `PASS_PRODUCT_TRACE / STOP_SOURCE_OR_CONTRACT`. Это пилот качества представления на четырёх исторических задачах. Единица сравнения — участник. Установки и исторические окна не считаются независимыми зданиями или повторными независимыми испытаниями детектора.

## Задачи и условия

| Случай | Источник и сигнал в обоих условиях |
| --- | --- |
| A | Stage02 LBNL, `coi_bias_2_annual.csv`, 2018-10-20. SAT_ONLY, `MODEL_ANOMALY` на 955 минутах. D002 остаётся открытым. |
| B | G36 Stage06/07, `BaselineSystem.csv`. Сохранённый нормальный прогон и семь блочных тревог. Эксплуатационное наблюдение `ABSTAIN`. |

| D | Mendeley V1 Stage09/10, `event-AHU2`. `ABSTAIN`. |

Оба условия используют тот же загрузчик BP-15 и одинаковые вопросы для каждого случая. **Signal-only** показывает код наблюдения. **Evidence-to-Action** показывает тот же код плюс телеметрию, качество, проверяемые факты, версии и происхождение, а также отдельный статус физической причины. Три варианта ответа выбирает сам участник, по одному на каждый вопрос. Готовые рекомендации, итоговые инженерные заключения, сводка ключа, ссылки для перехода к оригинальному экрану и обратная связь об оценке исключены из стимула. В расширенном условии признаки для вывода остаются доступны по замыслу эксперимента. Например, отображаются блочные тревоги, а готовый вердикт о допуске G36 опущен. В обычном BP-15 сохраняется полное представление.

## Назначение

Четыре порядка случаев по квадрату Уильямса. Каждая упорядоченная соседняя пара разных случаев встречается один раз среди четырёх порядков. Для каждого порядка есть два дополняющих варианта интерфейса: S–E–E–S и E–S–S–E. Каждый участник видит каждый случай один раз, два раза в S и два в E. В полном блоке из восьми каждый случай и позиция представлены одинаково в обоих условиях, первое условие сбалансировано, переходы S→E/E→S и S→S/E→E симметричны. Дизайн не устраняет обучение, усталость или эффекты более высокого порядка. [Williams, 1949](https://doi.org/10.1071/CH9490149)

| Код | Порядок | Условия |
| --- | --- | --- |
| 1 | A B D C | S E E S |
| 2 | A B D C | E S S E |
| 3 | B C A D | S E E S |
| 4 | B C A D | E S S E |
| 5 | C D B A | S E E S |
| 6 | C D B A | E S S E |
| 7 | D A C B | S E E S |
| 8 | D A C B | E S S E |

До приглашения перемешать коды внутри каждого блока и выдавать по порядку явки после согласия. Цель пилота — два блока, 16 человек, с промежуточной проверкой только технической полноты после первого. При меньшем наборе указать фактически использованные коды и неполноту блоков. Использованный код не назначается повторно после прерывания. Внешний вид условий различим. Ведущий работает по фиксированному сценарию и не даёт подсказок. Позиция ключа для каждого вопроса фиксирована внутри случая и сбалансирована по A–D, распределение не зависит от условия.

## Метрики и правило анализа

- Первичный результат — разность долей правильных решений E − S на участника по двум заданиям каждого условия. Сводка показывает распределение парных разностей и разрезы случай × условие × позиция с явными знаменателями.
- Вторичные результаты — доля необоснованных физических или причинных утверждений, доля корректных отказов и доля правильного следующего измерения. Разметка закрытых вариантов по отдельному ключу. Ошибка решения сама по себе не считается причинным утверждением.
- Время решения — целые миллисекунды по монотонным часам браузера от появления стимула с формой до первого валидного подтверждения. Загрузка источника и переходы исключены. При уходе вкладки в фон время продолжает идти, а испытание помечается прерванным для анализа времени. Ответы такого задания остаются в анализе корректности. Сравнить медианы времени среди непрерванных заданий с указанием числа исключений. Прерванная сессия без полной выгрузки учитывается в агрегированном журнале потока, без импутации ответов.
- Цель пилота — осуществимость и описание наблюдаемых результатов для этих случаев. Без реальных участников отсутствуют наблюдения об эффективности интерфейса. На этом объёме не заявляется улучшение в популяции. Идея показывать границы выводов согласуется с принципами объяснимости NIST. [NISTIR 8312](https://doi.org/10.6028/NIST.IR.8312)

## Границы и ключ

[Ключ ведущего](SCORING_KEY_16.md) основан на независимом чтении зафиксированных первичных материалов и предыдущих артефактов, отдельно от текстов экрана участника. Ключ публичен для аудита GitHub и хранится вне сборки интерфейса. Участникам передаётся только локальный адрес сеанса. Пилот требует контролируемой среды без просмотра исходников, GitHub, других страниц Investigator и обсуждения между участниками.

Решения относятся к историческим данным. A остаётся условным сопоставлением архива. B — один нормальный симуляционный прогон. C и D — два AHU одной площадки за один день. Интерфейс не собирает имя, контакты, демографию, свободный текст, идентификатор установки пользователя или абсолютные метки времени. Сохраняются технический случайный UUID сессии, код назначения, коды вариантов, статус стимула, длительность и флаг прерывания. Выгрузка — локальный файл после четырёх подтверждений, без сетевой отправки ответов.
