### 3. Протокол ДО первого экспериментального запуска — GATE 8A.2

До обучения и до просмотра метрик кандидатов создай `research/protocols/stage8a_control_effort_v1.md` и не редактируй задним числом; последующие изменения только addendum с указанием, что узнали.

#### 3.1. Гипотеза

H5a (exploratory): в CSIRO при проверенных управляющих каналах невязка команды контроллера относительно нормального контекста несёт новую информацию о fault events, не обнаруженных температурным residual. H5b (separate confirmatory): тот же предопределённый класс правил и параметров обнаруживает часть неисправностей другой установки AHU10 при локальной калибровке нормы без использования целевых fault labels.

**Не обещай улучшения и не заявляй перенос на другое здание:** AHU9/AHU10 — установки одного объекта.

#### 3.2. Данные / разделение

- AHU9 Stage6 held-out уже изучен. Используй его только как `EXPLORATORY_DEVELOPMENT`, не называй новым независимым подтверждением.
- Для AHU10 заранее выбери и сохрани **временные/событийные** Train Local, Validation Local и Held-Out Test без пересечения и с embargo около fault injection. Если не хватает нормальных периодов/событий — объяви `INDEPENDENT_TEST_NOT_FEASIBLE`, используй leave-one-whole-event-out как exploratory и не заявляй подтверждения H5b.
- По возможности используй AHU10 только один раз для финального сравнения после заморозки алгоритма на AHU9 и локально допустимой нормальной калибровке AHU10. Любые обучающие/валидационные нормальные интервалы AHU10 должны быть заранее перечислены и отделены от теста.
- Документируй ограничения переноса: установка, управляющая стратегия, доступные физические сигналы и единицы.

#### 3.3. Разрешённые признаки

Ввод `u_hat`: наружная температура OA, возвратная температура RA, уставка притока (если доказана семантика и не подменяется fault injection), состояние вентилятора, режим охлаждения/нагрева, временные признаки, допустимые лаги стабильных экзогенных каналов. Вводить `SA_TEMP` или `MA_TEMP` можно только после отдельного анализа, не маскирует ли симптом неисправности и не дублирует ли целевой канал; если опасность target leakage/contamination — исключить из первичного baseline. **Не используй** метку fault, номер эксперимента, сценарий, filename, random-injection parameters, post-proxy self-target и текущую/будущую команду для её же прогноза. Историческую команду использовать только как заранее обозначенную абляцию, поскольку она может скрыть устойчивую поломку.

#### 3.4. Сравниваемые методы — СТРОГО три

1. `T_ONLY`: существующий температурный детектор (для каждого источника применимая, локально откалиброванная версия; на одних и тех же точках и событиях);
2. `U_ONLY`: один простой `u_hat` — сначала Ridge/HistGradientBoosting/LightGBM небольшой сложности и только один основной вариант, выбранный по нормальной валидации; оцениваем `r_u=u_actual-u_hat`;
3. `T_PLUS_U`: заранее определённая комбинация нормированных `abs(r_T)` и `abs(r_u)` (`max` или простой L2); без постфактум подбора весов по тестовым fault labels.

Если после Gate 8A.1 нет надежного pre-proxy `u`, вместо `u_hat` выполнить семантический отрицательный результат. Запрещено притворяться, что есть настоящая управляющая команда. Следующая ветка возможна только после отдельного согласования alternative physical residuals.

#### 3.5. Калибровка

- Пороги и масштабы residual определять на исправной Validation Local; фиксировать до Test.
- Использовать одинаковую каузальную фильтрацию K-of-N и одинаковую политику закрытия/слияния эпизодов, иначе сравнение несправедливо.
- Нормировать residual на масштаб здоровой валидации, отдельно для рабочих режимов **только если** этих режимов достаточно в данных.
- Целевая проверка: рост Event Recall против T_ONLY **при** Pointwise FAR ≤5% и без роста ложных эпизодов/рабочий день относительно того же T_ONLY на том же тесте. 5% — исследовательский ограничитель, НЕ промышленный универсальный норматив.

#### 3.6. События и метрики

- Первичная единица оценки: **целое fault event**. Настройку алгоритма запрещено производить на сохранённых test event labels.
- Event обнаружен, если тревога нового детектора началась в размеченном `[start,end)` и соблюдено заранее заданное правило задержки/устойчивости. Допуск после окончания события устанавливать заранее, по умолчанию 0 для primary analysis; отдельная sensitivity analysis допустима.
- Метрики: Event Recall по всем faults, Event Recall по fault family/severity, Pointwise FPR на *исправных работающих* минутных точках, False Alarm Episodes per 8h-equivalent operating time, time-to-detect, median onset lag, coverage of comparable usable events. Для нулевого знаменателя — `NA`, не 0.
- Учитывать off/gap/overlap; не сшивать ночи в один event. Показывать исходное количество эпизодов, исключённые и почему, `N` для каждого метода.
- Сравнивать модели на одинаковой совокупности eligible events, а не лучшее подмножество для каждой.
- Доверительные интервалы/разброс считать на уровне целых событий или дат/объектов; тесты по минутным строкам не дают независимых p-values. При маленьком N сообщать только описательные оценки, без `p<0.05`.
- В отдельном отчёте показывать как были обнаружены новые (ранее пропущенные) события, так и то, какие потеряны относительно T_ONLY.

**PASS Gate 8A.2:** полный протокол создан до обучения/подбора; содержит формулы, списки файлов, дат, метрики, пороги, прогнозируемые ограничения и флаги `EXPLORATORY`/`CONFIRMATORY`.

### 4. Минимальная настоящая реализация — GATE 8A.3

Создай самостоятельный пакет `ml/control_aware/` (точные модули корректируй под структуру репозитория, но объясни соответствие):

```
ml/control_aware/
    __init__.py
    channel_semantics.py
    dataset.py
    splits.py
    features.py
    baseline_control.py
    residuals.py
    alarm_policy.py
    events.py
    evaluate_stage8a.py
```

Требования к реализации:

1. `channel_semantics.py`: читает проверенный манифест каналов, исключает banned/proxy/fault labels из ML input, выдает понятные ошибки при `UNKNOWN` вместо молчаливой подстановки.
2. `dataset.py`: извлекает временные ряды только с разрешёнными каналами и возвращает список исключённых точек с причиной, не смешивает AHU9 и AHU10, не импортирует весь raw в PostgreSQL.
3. `splits.py`: сериализует frozen chronological/event split и валидирует непересечение и embargo.
4. `features.py`: лаговые/дифференциальные признаки строго из доступных прошлых отсчетов, не использует будущие значения и запрещённые метки. Не делать target-авторегрессию по умолчанию.
5. `baseline_control.py`: простой базовый прогноз нормальной управляющей команды с параметрами, фиксированными seed, version и feature manifest. В идеале один Ridge и один маленький LightGBM-кандидат на здоровой валидации, финально выбрать один до оценки fault-test.
6. `residuals.py`: signed и absolute residual с единицами, валидным healthy scale; комбинация T+U не должна использовать невалидные residual и NaN вместо доказательств.
7. `alarm_policy.py`: причинный K-of-N фильтр, reset при gap/off, suppression/refractory задан явно; логика одинаковая для всех методов.
8. `events.py`: детерминированный скоринг по размеченным episodes и operating minutes без двойного счёта overlapping alarms, per-fault report и таблица false episodes.
9. `evaluate_stage8a.py`: CLI для повторения эксперимента, сохраняет JSON/CSV и два-три PNG-графика; не перезаписывает ранее зафиксированные `stage7_*.json`.

Прежде чем добавлять что-либо в API/UI, добейся воспроизводимой работы CLI. Всё подключение к существующему приложению — только после Stage 8A acceptance и отдельного подтверждения пользователя.

### 5. Негативные контроли и автотесты — GATE 8A.4

Нужны реальные pytest (тестовые синтетические таблицы допустимы *для unit*, не для научного результата):

- No proxy/label injection features (fail closed).
- Command self-leakage test: текущее/будущее `u` не попадает в `X` для прогноза `u`.

- Permutation/temporal-shift negative control: по нарушению временной зависимости результат ожидаемо ухудшается; если нет — объяснить, без подгонки.

### 6. Порядок эксперимента — GATE 8A.5
