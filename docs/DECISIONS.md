# DECISIONS — Архитектурные и технические решения BuildingPulse AI

### 1. Формат хранения временных рядов: Apache Parquet
- **Решение:** Для хранения временных рядов используется колоночный формат Parquet с компрессией Snappy/zstd.
- **Причина:** Реляционная БД (PostgreSQL) не оптимизирована для хранения миллионов минутных записей телеметрии на одну установку (в годовом файле LBNL ~525 600 строк × 31 колонка). Parquet обеспечивает компрессию в 5-10 раз, быстрый доступ к выбранным колонкам без чтения лишних данных и прямую интеграцию с Pandas / Polars / PyArrow.

### 2. Хранение каталога метаданных: PostgreSQL + SQLite fallback
- **Решение:** Метаданные (датасеты, сценарии, каналы, записи импорта, события качества данных и диагностические метки) хранятся в реляционной БД через SQLAlchemy 2.0.
- **Причина:** Поддерживается PostgreSQL для Docker Compose и SQLite (`sqlite:///./buildingpulse.db`) для быстрого локального запуска без внешних зависимостей.

### 3. Обработка временных меток и часовых поясов
- **Решение:** Временные метки хранятся в формате ISO 8601 (`YYYY-MM-DDTHH:MM:SS`). Если исходный датасет не специфицирует timezone (как симуляция LBNL, где даны локальные даты Chicago TMY без явного смещения UTC), в метаданных сценария фиксируется `timezone_status: "unknown"` (или "unspecified_local"). Мы **не присваиваем UTC или произвольный часовой пояс наугад**.

### 4. Алгоритм прореживания (Downsampling) телеметрии: Min/Max Bucket
- **Решение:** Для ограничения `max_points` (по умолчанию 1500 точек на канал) реализуется bucket-based downsampling, сохраняющий как минимальные, так и максимальные экстремумы внутри каждого временного сегмента (а также первую и последнюю точку интервала).
- **Причина:** Простое равномерное прореживание (каждая N-я точка) теряет кратковременные пики, выбросы и аномалии, критичные для диагностики AHU. Сохранение экстремумов гарантирует визуализацию всех аномальных всплесков при масштабировании года в окно браузера.

### 5. Разделение Ground Truth и вывода системы
- **Решение:** Поля `source_fault_label` (из датасета) и `detected_event` (результат правил) строго разделены на уровне схемы БД, API-контракта и интерфейса.
- **Причина:** Предотвращение утечки истинных меток в диагностический контур и защита от ложного впечатления, что простое правило "знает" истинный диагноз.

### 6. Расхождение инвентаря LBNL: PDF vs ZIP
- **Решение:** В документации и словаре каналов зафиксировано: в PDF таблице 4 указаны имена `sa_bias_*_annual.csv`, однако в фактическом ZIP архиве `LBNL_FDD_Data_Sets_SDAHU.zip` они названы `coi_bias_*_annual.csv`. При парсинге архива система использует фактические имена файлов архива и сопоставляет их с описанием температурных смещений.

### 7. Изоляция портов
- **Решение:** Для приложения назначены порты `WEB_PORT=5180`, `API_PORT=8050`, `DB_PORT=5455`.
- **Причина:** Порты 3000, 5173, 5432, 8000 заняты сторонними процессами на хосте пользователя.

### 8. Оптимизация Dockerfile: отказ от apt-get в пользу Python Wheels
- **Решение:** В `backend/Dockerfile` исключен вызов `apt-get update && apt-get install curl build-essential`. Все зависимости (pandas, pyarrow, psycopg, sqlalchemy) устанавливаются через готовые бинарные wheels, а healthcheck выполняется встроенным модулем Python `urllib.request`.
- **Причина:** Устранение зависимости от доступности зеркал debian (`deb.debian.org`) и прокси-настроек хоста Docker Desktop, существенное ускорение сборки и уменьшение итогового размера образа.

### 9. Архитектура и признаки виртуального датчика SA_TEMP
- **Решение:** Модель обучается исключительно на легкодоступных входах базовой автоматизации (Basic Set): `MA_TEMP`, `OA_TEMP`, `RA_TEMP`, `CHWC_VLV_DM`, `OA_DMPR_DM`, `SF_SPD_DM`, `SA_TEMPSPT`. Целевая переменная `SA_TEMP`, ее лаги и скользящие статистики категорически исключены из признаков.
- **Причина:** Предотвращение авторегрессионной утечки (target leakage). Виртуальный датчик должен восстанавливать тепловое состояние физически независимыми узлами смешения и теплообмена.

### 10. Хронологический блочный сплит (Block Temporal Split)
- **Решение:** Запрещен случайный сплит минутных точек (`shuffle=True`). Разделение производится непрерывными временными блоками: Train (дни 1–9), Validation (дни 10–11), Held-out Test (дни 12–14).
- **Причина:** Временные ряды HVAC обладают сильной минутной автокорреляцией. Случайное перемешивание приводит к фиктивно идеальным, невоспроизводимым в реальности метрикам.

### 11. Эксплуатационный фильтр (Operational Gating)
- **Решение:** Обучение и детекция выполняются только при работающем приточном вентиляторе (`SF_SPD_DM >= 0.5`). При выключенном вентиляторе возвращается статус `AHU_OFF` без генерации ложных тревог.
- **Причина:** При остановленном вентиляторе движения воздуха в установке нет, теплообмен затухает, а температура датчика дрейфует к температуре помещения.

### 12. Многовариантная калибровка порогов и причинный фильтр постоянства
- **Решение:** Пороги невязки ($3\sigma$, $Q_{95}$, MAD, $Q_{99}$) калибруются строго на валидационном интервале нормы. Выработка тревоги требует превышения порога минимум $K=10$ минут из скользящего окна $N=15$ минут.
- **Причина:** Фильтрация одиночных переходных всплесков без использования будущих точек. Предоставление исследователю консервативного ($3\sigma$) и чувствительного ($Q_{95}$) режимов.

### 13. Невязка как детектор, а не изолятор (No Fault Guessing)
- **Решение:** В API и интерфейсе события превышения порога явно маркируются как «Отклонение модели виртуального датчика» с обязательным научным дисклеймером.
- **Причина:** Экспериментально доказано, что заклинивание клапана, заслонки и смещение датчика вызывают одинаковое увеличение скалярной невязки. Присваивание ярлыка «сломан датчик» только по невязке научно некорректно.

### 14. Защитный барьер домена (UI Domain Guard)
- **Решение:** Для моделей, обученных на симуляции LBNL SD-AHU, при выборе сценариев с `source_kind != 'SIMULATED_BENCHMARK'` (например, `SYNTHETIC_DEMO` или загруженный пользователем CSV) интерфейс и бэкенд по умолчанию блокируют отображение невязок как валидированных ML-тревог. Возвращается статус `OUT_OF_DOMAIN_UNVALIDATED`.
- **Причина:** Предотвращение ложного впечатления о качестве модели при работе на принципиально несогласованном физическом домене. Возможность включения исследовательского режима только по явному запросу пользователя с сохранением предупреждения.

### 15. Многосезонный сплит (Multi-Season Temporal Split)
- **Решение:** Обучение и валидация виртуального датчика `vs-sa-temp-v2` переведены на схему `MultiSeasonTemporalSplit`, охватывающую 4 сезона (Зима: январь, Весна: апрель, Лето: июль, Осень: октябрь) со сплитом внутри каждого сезона: 9 дней Train, 2 дня Val, 3 дня Held-out Test.
- **Причина:** Устранение сезонного смещения (Winter-only Bias) и проверка тепловой модели в условиях активного механического охлаждения (`CHWC_VLV_DM > 0`).

### 16. Схема независимого сплита сценариев (Scenario-Level Split)
- **Решение:** Классификатор семейств неисправностей обучается на одних уровнях дефектов (25% и 75% stuck, $\pm 4^\circ\text{C}$ bias), а оценивается на строго отложенных независимых сценариях (10% и 50% stuck, $\pm 2^\circ\text{C}$ bias).
- **Причина:** Исключение утечки между обучающей и тестовой выборкой. Случайное разбиение строк одного файла не позволяет проверить обобщающую способность алгоритма на новые дефекты.

### 17. Сохранение неразрешенных состояний (UNRESOLVED Policy)
- **Решение:** В инженерном бейзлайне правил при недостатке или противоречивости физических свидетельств система возвращает статус `UNRESOLVED` вместо принудительного выбора класса наугад.
- **Причина:** Честное отражение фундаментальных ограничений наблюдаемости (Basic Profile) без создания иллюзии 100% точности.

### 18. Формальный Evidence-Aware Decision Layer
- **Решение:** Вместо принудительной классификации $\arg\max_c P(c)$ внедрен формальный слой решений, который сопоставляет скоры ML-модели, физические свидетельства приводов ($CHWC\_VLV$, $OA\_DMPR$), тепловой баланс и качество данных, вырабатывая категории `SINGLE_CAUSE`, `MULTIPLE_PLAUSIBLE`, `CAUSE_UNRESOLVED`, `NO_ANOMALY`.
- **Причина:** Доказано экспериментально, что принудительный выбор на базовом профиле `BASIC` приводит к риску ошибки более 54% при высоких уровнях охвата.

### 19. Строгая изоляция каналов профилей наблюдаемости (Hidden-Channel Guard)
- **Решение:** Для каждого профиля (`BASIC`, `BASIC_PLUS_VALVE`, `BASIC_PLUS_DAMPER`, `BASIC_PLUS_BOTH`, `FULL`) реализована строгая фильтрация DataFrame по белому списку разрешенных каналов в `SensorProfileRegistry`. Любые обращения к колонкам обратной связи при профиле `BASIC` блокируются на уровне пайплайна.
- **Причина:** Предотвращение скрытой утечки информации через вспомогательные фичи. Доказано регрессионным тестом: искажение колонок обратной связи не влияет на вывод профиля `BASIC`.

### 20. Метрики селективной классификации (Selective Risk–Coverage)
- **Решение:** Оценка качества локализации стандартизирована в рамках теории селективной классификации (Selective Classification / Rejection): $\text{SelectiveCoverage} = |A_\tau| / |D|$ и $\text{SelectiveRisk} = \text{errors} / |A_\tau|$, где $D$ — истинно аномальные обнаруженные окна.
- **Причина:** Позволяет честно сравнивать Decision Layer с baseline-стратегиями отказа B1 (Confidence-only) и B2 (Margin/Entropy rejection) при одинаковом контролируемом уровне охвата.

### 21. Логика физического опровержения (Physical Refutation)
- **Решение:** При наличии датчика обратной связи положения штока клапана ($CHWC\_VLV$), если рассогласование с командой составляет менее 5% ($|CHWC\_VLV\_DM - CHWC\_VLV| < 0.05$), гипотеза заклинивания клапана физически исключается из множества жизнеспособных кандидатов, что устраняет неоднозначность в пользу температурного смещения датчика.
- **Причина:** Экспериментально доказано, что это снижает Selective Risk при Coverage = 0.60 с 0.361 до 0.195, а F1 смещения датчика возрастает с 0.1886 до 0.5396.

### 22. Статус Conformal Prediction как Exploratory
- **Решение:** Из-за ограниченного количества независимых физических сценариев (по 4 интенсивности на класс в симуляции LBNL) и автокорреляции минутных точек метод Split Conformal зафиксирован как исследовательский прототип без декларирования формальных вероятностных гарантий покрытия на новых зданиях.
- **Причина:** Соблюдение научной честности: предпосылка независимости и одинаковой распределенности (i.i.d.) для минутных временных рядов HVAC нарушается.

### 23. Динамическая верификация отслеживания привода (Dynamic Tracking vs Static Zero-Excitation)
- **Решение:** В модуль `ml/diagnostics/evidence.py` внесено строгое требование: статус слежения за командой (`tracking`) объявляется только в том случае, если размах изменения команды в окне удовлетворяет критерию динамического возбуждения ($\Delta \text{cmd} = \max(\text{cmd}) - \min(\text{cmd}) \ge 0.15$). Если команда постоянна ($\Delta \text{cmd} < 0.15$), совпадение положения и команды расценивается как `INSUFFICIENT_ACTUATOR_EXCITATION`, что категорически запрещает ложное опровержение заклинивания штока.
- **Причина:** Устранение дефекта Stage 4, когда клапан, застрявший в закрытом положении ($pos=0$), при нулевой ночной команде ($cmd=0$) ложно объявлялся исправно работающим и отслеживающим сигнал.

### 24. Разделение дефектов штока и седла клапана (Stuck vs Leakage)
- **Решение:** Дефект заклинивания штока (`VALVE_STUCK`) отделен от дефекта неплотности посадки седла клапана (`VALVE_LEAKAGE`). Опровержение по совпадению датчика штока применяется исключительно к `VALVE_STUCK`. Для `VALVE_LEAKAGE` датчик положения штока $CHWC\_VLV = 0$ не является опровержением, поскольку утечка жидкости происходит через физический зазор при полностью закрытом штоке.
- **Причина:** Физическая достоверность: идеальное положение штока в нуле не исключает эрозию или засор седла теплообменника.

### 25. Эмпирическая оценка ценности каналов на валидации (Validation-Grounded Information Value)
- **Решение:** Выбор рекомендуемого для дооснащения датчика производится на основе предрегистрированного функционала $V_j(c) = \Delta \text{SelectiveRisk}_j(c)$ при фиксированном целевом охвате $c=0.60$, рассчитанном строго на независимой валидационной выборке симулятора ($V_{\text{valve}} = 0.203$ vs $V_{\text{damper}} = 0.021$).
- **Причина:** Обеспечение строгой причинно-следственной изоляции (zero test leakage): ранжирование кандидатов формируется до ознакомления с тестовыми сценариями.

### 26. Негативный трансфер и доменный барьер для полевой телеметрии (Field BMS Transfer Guard)
- **Решение:** Попытка прямого применения ML-модели виртуального датчика `vs-sa-temp-v2` (обученной на EnergyPlus LBNL) к полевой телеметрии реального австралийского здания CSIRO AHU9 приводит к катастрофическому падению точности (MAE = 4.47 °C vs 0.039 °C, $R^2 = -1.92$, 98.6% ложных тревог). В системе зафиксирован строгий отказ (Abstention) с кодом `OUT_OF_DOMAIN_UNVALIDATED` и статусом `OUT_OF_DOMAIN` для рекомендателя.
- **Причина:** Предотвращение ложного переноса лабораторных выводов на реальные объекты с иной аэродинамикой, типоразмерами змеевиков и климатическими условиями без локальной калибровки.

### 27. Физическая реконструкция температуры смешанного воздуха (CSIRO MA_TEMP Physical Reconstruction)
- **Решение:** Обнаружено аппаратное дублирование в исходной BMS-выгрузке CSIRO AHU9: `AHU9ahuMaTemp` и `AHU9ahuSaTemp` абсолютно идентичны ($\Delta = 0.000^\circ\text{C}$ на всех 457 653 строках), так как физический датчик до змеевика отсутствует. Для устранения искусственной утечки таргета и некорректного ввода модели LBNL в заблуждение выполнена физическая реконструкция температуры смеси по уравнению теплового баланса камеры смешения:
  $$\hat{T}_{ma} = \alpha T_{oa} + (1-\alpha) T_{ra}, \quad \alpha = \text{clip}(OA\_DMPR\_DM, 0.10, 1.0)$$
- **Причина:** Использование псевдо-датчика приводило к тому, что входная температура $T_{ma}$ равнялась уже охлажденной температуре $T_{sa}$, что заставляло модель предсказывать дальнейшее охлаждение и формировало систематический положительный сдвиг прогноза (+4.46 °C).

### 28. Превосходство аффинной и константной адаптации над чисто локальной линейной моделью
- **Решение:** В качестве основного метода адаптации исходной модели симулятора LBNL приняты методы C2 (Affine Calibrator, $y_{\text{adapt}} = 2.0138 \hat{y} - 10.1104$, MAE = 1.11 °C) и C1 (Constant Bias, $y_{\text{adapt}} = \hat{y} + 4.5933$, MAE = 1.20 °C, лучший RMSE = 1.60 °C), существенно превзошедшие локальную линейную Ridge-модель L1 без источника (MAE = 2.98 °C).
- **Причина:** Предобученная на многосезонной физической симуляции модель `vs-sa-temp-v2` содержит богатые нелинейные паттерны взаимодействия каналов, которые сохраняются даже при смещении рабочей точки. Простая аффинная калибровка требует минимального объема локальной нормы (1 неделя) и исключает риск переобучения. Ранее упоминавшиеся в черновиках числа 0.582 и 2.459 являлись опечаткой и официально заменены фактическими параметрами артефакта.

### 29. Локальная калибровка диагностических порогов ($3\sigma$ Empirical Thresholding)
- **Решение:** Диагностические пороги обнаружения аномалий $\tau = 3\hat{\sigma}_{val}$ калибруются исключительно по валидационной выборке нормального режима здания-реципиента (Val Local), а не переносятся со здания-источника LBNL.
- **Причина:** Исходные пороги LBNL ($\pm 0.12^\circ\text{C}$) приводили к 100% ложных тревог на реальном здании из-за естественного технологического шума и нестабильности потоков реальной BMS. Локальный порог ($\tau = 3.01^\circ\text{C}$ для C2, $3.43^\circ\text{C}$ для C1) снизил уровень ложных тревог до 2.8%, уложившись в целевой инженерный бюджет $\le 5\%$.

### 30. Принятие инженерного компромисса чувствительности Неймана-Пирсона (FDD Sensitivity vs False Alarms)
- **Решение:** Система явно фиксирует компромисс между подавлением ложных тревог и чувствительностью к слабым дефектам. Адаптированный виртуальный датчик надежно детектирует грубые дефекты заклинивания охлаждающего клапана (CHW valve stuck 88%, recall 25.0% по непрерывному порогу невязки), однако не обнаруживает малые температурные дрейфы в обслуживаемых зонах, не выходящие за границы допустимого $3\sigma$-коридора естественной вариативности реального здания.
- **Причина:** Соблюдение научной честности: предотвращение фальсификации метрик или искусственного занижения порогов, которое разрушило бы эксплуатационную ценность системы ложными срабатываниями.

### 31. Физическая целостность визуализации временных рядов (Night-Gap Physics Integrity)
- **Решение:** В API `/api/adaptation/predictions` и ECharts включен принудительный разрыв непрерывных линий (`connectNulls: false` со вставкой точек `null` при интервалах $\Delta t > 30$ мин).
- **Причина:** Устранение искажающих реальность длинных диагональных прямых отрезков через ночные часы остановки вентилятора (с 18:00 до 06:00) и выходные дни.

### 32. Официальная фиксация отрицательного результата H4b

### 34. Безопасная маршрутизация адаптационных моделей и барьер доменной несовместимости (Stage 7.1)

### 35. Отзыв псевдореплицированного значения p < 0.05 в гипотезе H3 (Stage 7.1)

### 42. Научная ревизия методологии и исправление дефектов FDD на RBC-Nesbitt (Stage 8B-R.1)
- **Решение:**
  1. **Происхождение порогов и статус бенчмарка (P0-1):** Реализована независимая функция автоматического выбора порога по валидации `select_threshold(val_series, budget_far=0.03, candidate_grid)`. Доказано, что на валидационном дне чистой нормы при бюджете $\le 3\%$ выбираются $\tau=3.00$ для M2 ($\text{Val FAR}=2.43\%$) и $\tau=3.25$ для M3 ($\text{Val FAR}=0.00\%$).   2. **Доказательство строгого доминирования M2 над M3 (P0-2):** На сопоставимой сетке порогов $\tau \in [1.5, 5.0]$ доказано, что объединённый детектор M3 не добавляет ни одного события обнаружения относительно M2, при этом на всех рабочих порогах ($\tau \le 4.00$) имеет строго худший FAR. Запрещена некорректная механистическая трактовка невязки как доказанного «компенсирующего управления».
  6. **Наблюдаемость слабой аварии 30% (P0-6):** Доказано, что неисправность заслонки 30% непосредственно зафиксирована в телеметрии BAS приводов Col 73/74 (детекция 121/121 точек правилом `RELIEF > 20 | RETURN > 20`). Зафиксировано отсутствие статистической значимости превосходства M2 над M1.
  8. **Алгоритмические правки (P1-10, P1-11):** Внедрён изолированный подневный расчёт ложных эпизодов без слияния тревог через аварийные границы; математически зафиксировано различие нормировочных коэффициентов $\text{std}(|e|)$ и $\text{std}(e)$.
  9. **Сборка независимого пакета `BUILDINGPULSE_AUDIT_STAGE_8B_R_1.zip`:** Сформирован архив размером 1.69 MB (173 файла, SHA-256 проверен), включающий полноценный `requirements.txt`, исполняемый сьют из 110 Pytest, валидационные скрипты и отчеты.

### 45. Независимая предрегистрированная внешняя валидация на новых данных RBC-Nesbitt (Stage 8B-R.4)
- **Решение:**
  1. **Исправление дефекта NaN в DomainGuard:** В `CalibratedDomainGuard.check_point()` введена явная проверка конечной валидности (`not np.isfinite(val)`, отсутствие ключа, некорректный тип данных), гарантирующая присвоение статуса `INVALID_INPUT` / `UNRESOLVED` с `is_ood=True`, исключая ложную классификацию повреждённых измерений как `IN_DOMAIN`.
  2. **Политика разрывов телеметрии:** Зафиксирована пороговая длительность физического разрыва: единичные пропуски $\le 10$ минут сохраняют контекст (поглощение джиттера BACnet), интервалы $\ge 15.0$ минут вызывают строгий сброс причинной памяти K-of-N и разделение ложных эпизодов на непрерывной календарной сетке. Добавлены регрессионные тесты для интервалов 5, 10, 15 и 20 минут (`test_domain_guard_nan_and_gap_policy.py`).
  3. **Строгое разделение выборок (Pre-registered Disjoint Split):** 4 исторических аварийных дня разработки объявлены `DEVELOPMENT-KNOWN` и исключены из подтверждающего теста. Из официального каталога Drexel Figshare (DOI: 10.6084/m9.figshare.57268553) извлечены 13 ранее не исследованных файлов: 5 аварийных сценариев (Лето: Stuck 90%, Stuck 60%, TSup bias -3.5°F; Зима: Stuck 90%, Stuck 80%) и 8 базовых нормальных дней (Лето, Зима, Весна).
  4. **Заморозка алгоритмов и порогов (Zero Post-Hoc Tuning):** Модели M1, M2, M2 No-MA, M3, M6 и пороговые значения зафиксированы по обучающе-валидационной выборке разработки. Подбор порогов по независимому холдоуту исключён.
  5. **Результаты многосезонной валидации:**
     - *Летний срез (внутри домена):* M1 Thermal даёт Recall 66.7% (2/3) с FAR 8.05%; M6 Direct Damper BAS даёт Recall 66.7% с задержкой 7.5 мин и FAR 0.00%.      - *Зимний срез (сезонный OOD):* Продемонстрирован межсезонный сдвиг распределения температуры $T_{oa}$ (0–10°C против летних >20°C). ### 47. Обработка нулевых знаменателей в метриках при нулевом охвате DomainGuard
- **Решение:** Если фильтр применимости или DomainGuard отсекает все точки нормального или аварийного периода (`eligible_points = 0`), метрики `pointwise_far` и `pointwise_recall` сериализуются строго как JSON `null` со статусом `NOT_EVALUABLE_ZERO_COVERAGE`.
- **Причина:** Деление 0/0 математически неопределено. Вывод 0.00% является научной фальсификацией, скрывающей полную абстиненцию модели.

### 48. Принцип разделения официального окна аварии и физического оверрайда
- **Решение:** В отчётах всегда представляются две величины: New Onset Recall по официальным границам испытания (например, 10:00) и чувствительность к физическому воздействию (09:55). Если до 09:55 детектор имел высокую частоту ложных тревог (как зимой при OOD), срабатывание в 09:55 не может объявляться успешной детекцией аварии.
