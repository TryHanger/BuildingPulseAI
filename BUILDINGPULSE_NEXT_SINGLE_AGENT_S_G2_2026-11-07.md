## 1. Проект G2 — точные границы выводов

**Задачи:** режим работы командного сигнала вентилятора, переходная устойчивость, OAT context, качество данных и статус применимости конкретной проверки. **Не задача:** установить физический режим экономайзера, реальную работу компрессора/чиллера, факт полного открытия заслонки, реальный расход воздуха или причину неисправности без соответствующих независимых сигналов.

Сначала перепроверь, является ли `SF_SPD_DM` в официальном LBNL каноном **доказательства фактической работы вентилятора** или командой/статусом контроллера. Если подтверждён только командный сигнал, называй вывод `FAN_COMMAND_ON/OFF`, не `FAN_PROVEN_RUNNING`. Для каждого решения сохраняй `source_signal_id`, `observation_kind`, `confidence_label` без выдуманной вероятности.

### 1A. Прозрачная детерминированная state machine

- Допустимые состояния обработки: `OFF`, `TRANSITION_HOLD`, `RUNNING` (только в документированном смысле входа), `UNKNOWN`. Если смысл `RUNNING` физически не подтверждён, замените его названием `FAN_COMMAND_ACTIVE` и обеспечьте обратную совместимость через версионированное поле. Запрещено называть этот результат `COOLING`/`ECONOMIZER` без независимых оснований.
- `SF_SPD_DM` ровно валидный бинарный 0/1; missing, NaN, inf, 0.5 и недостоверный канал → `UNKNOWN`, не «fan off». Временные точки строго возрастают, шаг LBNL — 60 с, source clock **без самодельного UTC**.
- Отсутствующий отсчёт, временной разрыв, смена 0→1, UNKNOWN→1 или новый диапазон анализа сбрасывают таймер непрерывного включения. Таймер никогда не использует будущие строки.
- Startup hold **5 минут только как предварительный инженерный параметр** `policy_version`; указать источник и статус `PROVISIONAL`, не писать «так требует LBNL». Граница применения — проверяемая: не применять SAT fault rule во время hold.
- `OA_TEMP` классифицировать относительно **33.8°F и 60°F**, как *погодный контекст* указанной последовательности. Входные значения в °F или надёжно преобразованные °C. Равенство порогам/округление следует проверять явно. `OA_TEMP` не доказывает mechanical cooling enable.
- `mechanical_cooling_enable = UNOBSERVED` и `economizer_actual_state = UNOBSERVED`, пока нет проверенного независимого сигнала и логики. При наличии только `OA_DMPR_DM` это **команда, не положение**. `SYS_CTL`, `CHWC_VLV` и ground truth не используются runtime в BASIC.
- Поведение на реальных исторических данных G2 сравнить с офлайн-метаданными режима **только в отдельном исследования-скрипте**, если допустимо, но такой сигнал не должен утечь ни в ответ runtime, ни в обучение.

### 1B. Data Quality — минимальные операционные проверки

- На исходных записях: валидность метки времени; дубликаты и немонотонность; пропуски и ожидаемый шаг; null/NaN/inf; корректный тип/диапазон бинарных команд; физически невозможные значения при доказанной семантике.
- На уровне метода выдавать `VALID | DEGRADED | INVALID | UNKNOWN` и причину, не глобально отключать все методы при проблеме одного канала. Постоянный бинарный OFF **не является** «stuck sensor». Constant analog может стать сигналом качества только после доказанной нормы поведения и выбранного окна.
- Сохранить блокировку давления/производных физически неоднозначных колонок (`SA_SP`, `SA_SPSPT`, `SA_CFM` и др.) и никаких pressure/flow fault rules.
- Ошибки преобразования Fahrenheit: абсолютная температура и *разность температур* преобразуются разными формулами. Для разрывов и пропусков не интерполировать измерения без явно указанной политики.

### 1C. Applicability engine — ещё не диагностика

Для каждого кандидата на правило (`running-command-range`, `sat-tracking`, `valve-tracking`, будущий `AHU-SATDEV`) вернуть типизированное:
`method_id, policy_version, status: APPLICABLE|INAPPLICABLE|INCONCLUSIVE, reason_code, missing_roles, mode_context, source_lineage, data_quality`.

`running-command-range` — это **проверка сигнала**, а не поломка оборудования. `sat-tracking` можно только считать применимым, если действительно подтверждены режим регулирования SAT, качество SAT+SP и отсутствие перехода; если режим неизвестен — `INCONCLUSIVE`. `valve-tracking` на BASIC — `INAPPLICABLE` из-за отсутствующего фактического положения, а не «клапан физически отсутствует». Отсутствие одного канала не подавляет независимые проверки.

Не выдавать `DETECTED`, `NO_ALARM` или cause claim для методов, которые не выполнялись или неприменимы. Не использовать произвольные `validated_discriminator`, `probability` или fictional GT.

## 2. Runtime API и фронтенд

1. Сохранить действующие **четыре** `/api/v1` операции, legacy `/api`, все старые страницы и типизированную выдачу OpenAPI. Не делать breaking change без записи в `API_CHANGELOG.md` и версионирования.
2. Добавить bounded endpoint `GET /api/v1/equipment/{equipment_id}/modes?dataset_id=...&start=...&end=...` с документированной шкалой `SOURCE_SIMULATION_TIME`, сегментами/окнами, `sample_seconds`, границами разрывов, версией state-policy и статусами UNKNOWN; не подменять исходную шкалу на UTC.
3. Расширить точечную диагностику **аддитивно**: `mode_context`, `data_quality`, `method_applicability` с привязкой к versioned evidence. `model_scope=UNKNOWN`, когда модель не проверялась. Сохранять действующие статусы причина `NOT_ASSESSED` там, где не проводилась причинная диагностика.
4. Изменить **в том же рабочем дереве** React Investigator / Replay, чтобы он показывал server mode, transition hold, unknown/exclusions, качество каналов, источник и версию. Моковые Incidents не превращать в реальные; на их экранах по-прежнему `DEMO_FIXTURE`.
5. Для окна прямого перехода к времени: state machine должна реконструировать корректный контекст с необходимым **историческим префиксом** для hold (либо достоверным checkpoint), а не ошибочно объявлять каждый запрос с середины года новым стартом. В ответе указать способ решения этой проблемы.
6. Не загружать весь год CSV на каждый вызов нового API; использовать проверенный Parquet window index, ограничить размер запросов, метить доступность данных.

## 3. Обязательные негативные и интеграционные тесты

Дополнить тесты следующими группами (на реальных или минимальных synthetic с чёткими ярлыками): fan0, fan1, null, 0.5, NaN/inf; переходы 0→1/1→0; дырка в 60-секундной сетке, boundary при пагинации и прямом seek; неизвестная/неверная OAT, 33.8°F, 60°F, значения по обе стороны; ночное циклирование; кратковременный фликер; командный сигнал vs физическое подтверждение; BASIC без `CHWC_VLV`; `SYS_CTL` как oracle не влияет на решения; недостоверный SAT не отменяет независимый сигнал другой проверки; команда saturation не доказывает заклинивание; API неизвестный dataset/equipment/invalid source time; zero-leakage, GT isolation и отсутствующие файлы.

Тесты должны подтверждать **точный API**, не только unit-функцию. Минимум: backend suite, contract/fixtures validation, TypeScript strict build, Playwright 1440/1280/1024/390 (или обоснованный эквивалент), smoke по HTTP настоящего v1 на исправных LBNL рядах. Все команды, версии и результаты записать. Не писать PASS, если запуск заблокирован средой или отсутствует нужный raw.

## 4. Приёмка G2 (GO/NO-GO)

**GO** только если:
- режимы доказуемы лишь в пределах доступных BASIC сигналов и никогда не названы фактическим охлаждением без независимого evidence;
- startup hold и разрывы корректны на старте и при seek/пагинации;
- качество и applicability по каждому методу сохраняют отрицательные/неопределённые результаты и не создают fault diagnosis;
- новая выдача описана в единой OpenAPI и интегрирована в React без потери старых страниц;
- raw/SQLite/Parquet исходного базового снапшота не изменились;
- тесты проходят в воспроизводимой среде либо известные блокеры честно указаны;
- научные ограничения и следующий безопасный переход к G3 представлены в решении `G2_GATE_RESULT.md`.

**NO-GO:** неизвестная интерпретация команд превращается в `fan proven`, OAT выдаётся за active economizer/cooling, missing data превращается в норму, тесты меняют рабочую SQLite, или UI показывает mock inference как реальное измерение.

- `SOURCE_MANIFEST.tsv` (included/omitted/changed), `README_REPRODUCE.md`, SHA256SUMS для включённых файлов;

**Запрет:** никакого commit, push, deploy, изменений production/OT и новой программы ML. Если физическое поведение не выводится из данных, честно возвращать UNKNOWN/INCONCLUSIVE и оформить конкретное data-requirement, а не «проверить методом тыка» известное ограничение.

## 6. Только после принятия G2

Следующая отдельная итерация — G3: выбрать 1–2 физически применимых и реально исполняемых правила APAR (или честные локальные SAT/command checks), применить их к известным режимам и построить событийную агрегацию без ложной локализации причин. G4: закончить цепочку dataset → real symptom → incident → evidence → replay → report. После G4 конкурировать Ridge/PCA/LightGBM, а не раньше.
