# BuildingPulse AI — обязательный горячий фикс Stage 8B-R.3 (не новый ML-этап)

Это узкое исправление P0, выявленного независимым повторным запуском Stage 8B-R.2. **Не начинай Stage 8C и Active Probing, не меняй модель или постфактум подобранные пороги.**

## Gate 0 — исправить потерю timestamp

В `scripts/evaluate_rbc_nesbitt_reconciled.py`, функция `load_clean_nesbitt()`, используется:

```python
dt_index = pd.to_datetime(dt_strings)
clean = pd.DataFrame(index=dt_index)
clean["timestamp"] = dt_index
```

Поскольку `dt_index` является `Series` с RangeIndex, pandas выравнивает значения по несовместимому `DatetimeIndex`. **Вся колонка `timestamp` = NaT (288/288 строк каждого реального CSV)!** Сам индекс DataFrame правильный, из-за чего эта ошибка маскируется в pointwise CSV.

Исправь присваивание без pandas index alignment (`pd.DatetimeIndex(dt_index).to_numpy()` либо равнозначное) и добавь тест на реальном CSV: все временные метки заполнены, строго возрастают, равны DataFrame.index и идут с шагом 5 минут. Добавь проверки недопустимых HHMM (например 12:60), дубликатов, неотсортированности, пропусков, DST/локальной временной зоны по необходимости.

## Gate 1 — доказать работоспособность Gap Guard и Latency

Добавь интеграционный тест через **тот же загрузчик**, который используют раннеры: после намеренно добавленного двухчасового разрыва для K=2/N=3 тревога не должна переносить историю через разрыв. При NaT сейчас получается ложная тревога.

Сверь точные задержки M2 tau=3.5 после исправления: 2017-07-18 = 30 минут, 2017-08-11 = 10 минут, 2018-07-10 = не обнаружено, 2018-07-11 = 50 минут (со спорной разметкой последнего). Могут измениться только при явном документированном изменении правил.

Запрети `NaN`/`Infinity` в машинном JSON (`allow_nan=False`), проверь сериализацию стандартным строгим парсером. В исходном Stage 8B-R.2 JSON было **398 литералов NaN**, включая задержки обнаружения. Непроверенные/неприменимые значения задавай `null` и отдельно объясняй причину.

## Gate 2 — вывести честные показатели DomainGuard

Отдельно для каждой конфигурации и даты вычисляй:
- сколько нормальных точек и сколько fault-точек были eligible;
- сколько OOD и сколько `OOD_ABSTAINED`;
- сколько подтверждённых тревог и задержку для каждого физического эпизода;
- `FAR (conditional on eligible)` **вместе** с coverage по норме и fault, не отдельно.

Контрольные числа для M2 in-domain tau=3.5: **313/680 = 46.0% coverage нормальных точек, 86/472 = 18.2% coverage fault-точек, FAR 0/313, recall 1/4**. Не использовать «0% FAR» как доказательство лучшего эксплуатационного качества. `OOD_ABSTAINED` и итоговая alarm/decision mask должны быть представлены в pointwise CSV (сейчас там только `VALIDATED_IN_DOMAIN` / `OOD_DETECTED`, без финальной тревоги).

`dev_envelope` (min-max по Train+Val) по определению включает 100% этих данных и не доказывает обобщение. Учти нормальные дни 20170618 и 20170702: на них выявлены OOD 16.7% и 26.7% соответственно, хотя модель не тревожит при tau=3.0; используй это только как **exploratory verification**.

## Gate 3 — устранить ложные научные гарантии

1. M2 — прогноз **feedback клапана CCV_FBK**, не исходной команды контроллера. Не называй это доказанной передачей модели Control Effort CSIRO → Nesbitt.
2. Сценарий 20180711 остаётся `LABEL_OR_SIGNAL_SEMANTICS_UNRESOLVED`; выводы 2/3 и 3/4 разделять.
3. `MA_TEMP` — потенциально эндогенный симптом; её абляция показывает зависимость обнаружения от признака, но не доказанную причинность.
4. Негативный Circular Shift перемешивает остатки относительно времени, не доказывает физический механизм.
5. Статистические числа, реальную режимную маску, N fault событий и все таблицы формируй из текущего `run_id`/манифеста **без жёстко прописанных выводов**, явно проверяя статусы по вычисленным метрикам.
6. В baseline оценке должен быть явный операционный guard для выключенного вентилятора; на этих четырёх днях SF_SPD >=30%, но контроль обязателен для новых данных.
